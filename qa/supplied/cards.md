# Cards

## Rule Description

Cards are used to preview and share content, and can include text, images, video, social media sharing options.

## Rule Type

atomic

## Accessibility Requirements Mapping

Required for conformance
- Outcome mapping:
    - Any failed outcomes: success criterion is not satisfied
    - All passed outcomes: success criterion needs further testing
    - An inapplicable outcome: success criterion needs further testing

## Input Aspects
- DOM Tree

## Applicability

This rule applies to any HTML page that includes a Cards component.

## Expectations

### Expectation 1

Cards that are presented as a set, i.e. there are multiple cards together, they must be marked up as unordered list (&lt;ul&gt;) with each card marked up as a list item (&lt;li&gt;).

### Expectation 3

The headline for a card must be the first text content (including alternative text for media elements) within a card's source order.

### Expectation 4

All headlines within a set of cards must be marked up with the same heading level.

### Expectation 5

A set of cards must be preceded by a heading describing the collection of the cards. The heading level must be one higher than the heading level of the headlines within the cards.

### Expectation 6

When an image is the focus of the card, it should be considered salient content and must include sufficient alternative text

## Card Test Cri­te­ria

ACT for Card components.

On this page

This document outlines the Accessibility Conformance Testing (ACT) for a card component within a web application, focusing on ensuring that the component meets the Web Content Accessibility Guidelines (WCAG) standards. The card component, a common UI pattern, must be accessible to all users, including those who rely on assistive technologies like screen readers.

### Introduction

The card component is a visually distinct block used to display related information in a compact format, typically as part of a larger collection of cards. Cards are widely used in web interfaces to present information succinctly, often acting as entry points to more detailed content. Given their visual nature, it's crucial to ensure that cards are designed and developed with accessibility in mind, providing equivalent experiences for users regardless of their method of interaction with the content.

### Accessibility Requirements

The Card component is evaluated against the following WCAG 2.2 success criteria, categorized under the Perceivable, Operable, Understandable, and Robust (POUR) principles:

#### Perceivable
- 1.1.1 Non-text Content: All non-text content that is presented to the user has a text alternative that serves the equivalent purpose, especially important for images within the card.
- 1.4.4 Resize Text: Text can be resized up to 200 percent without the use of assistive technology and without loss of content or functionality.
- 1.4.10 Reflow: Content must reflow in a way that it remains accessible and legible when the layout changes to a single column at 320 pixels width.
- 1.4.3 Contrast (Minimum): Text (and text in images) must have a contrast ratio of at least 4.5:1 against the background.
- 1.4.11 Non-text Contrast: The visual presentation of UI components (including borders, edges, and actionable items) must have a contrast ratio of at least 3:1 against adjacent colors.

#### Operable
- 2.1.1 Keyboard: All functionality of the content is operable through a keyboard interface without requiring specific timings for individual keystrokes.
- 2.4.3 Focus Order: If a web page can be navigated sequentially, components receive focus in an order that preserves meaning and operability.
- 2.4.7 Focus Visible: Any keyboard operable user interface has a mode of operation where the keyboard focus indicator is visible.
- 2.5.8 Target Size (Minimum): The clickable area of the Card must be at least 24 by 24 CSS pixels to be easily clickable or tapped.

#### Robust
- 4.1.2 Name, Role, Value: For all user interface components (including but not limited to: form elements, links, and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies.

### ACT Test Cases

#### Test Case 1: Keyboard Navigation and Focus

##### Objective

To verify that the card and its interactive elements can be navigated using a keyboard.

##### Test Steps
1. Use the keyboard to navigate to the card using the tab key.
2. Ensure it is possible to move the keyboard focus to each link within the card.
3. Confirm that you can use the keyboard to navigate to each link destination.
4. Test the functionality of keyboard modifier keys (e.g., accessing the context menu with Shift + F10).

##### Expected Results
- All interactive elements within the card should be reachable and operable using the keyboard.
- Navigating to and from the card and its elements does not disrupt the tab order or focus.

#### Test Case 2: Screen Reader Link Navigation

##### Objective

To ensure that links within the card are accessible and meaningfully labelled for screen reader users.

##### Test Steps
1. Open a screen reader and navigate to the card using the "navigate by links" menu.
2. Verify that all links within the card are visible to the screen reader.
3. Check that each link has a meaningful label that provides context (avoiding generic labels like "click here").

##### Expected Results
- Screen reader users should find all links within the card in the navigation menu.
- Links should have descriptive labels that convey their purpose or destination.

#### Test Case 3: Screen Reader Heading Navigation

##### Objective

To ensure that headings within the card provide a logical structure and context for screen reader users.

##### Test Steps
1. With a screen reader enabled, use the "navigate by headings" menu to find the card's heading.
2. Navigate to the card's heading and then proceed to move the screen reader cursor forward to explore the rest of the card's content.
3. Ensure that all meaningful content following the heading is accessible and logically ordered, including images with non-empty alt attributes.

##### Expected Results
- The card's heading should be detectable and navigable via screen reader.
- All subsequent content in the card, including text and images with meaningful alt texts, should be reachable and understandable when navigating from the heading.

Expectation 2

Each card must have a headline, and the headline must be marked up as a heading element (&lt;h2&gt;, &lt;h3&gt;, &lt;h4&gt;, etc.).

#### Test Case 4: Content Resizing Accessibility

##### Objective

To ensure the card's content remains accessible and legible when text is resized to 200%.

##### Test Steps
1. Use the browser settings to increase the font size to "Large" or set text size to 200% of its default size.
2. Inspect the card for any content clipping, overlapping, or other issues that could impact readability or usability.

##### Expected Results
- No part of the card's content becomes clipped, overlapped, or otherwise unusable at 200% text size.
- The layout adjusts to accommodate the increased text size while
- maintaining content accessibility and functionality.
