# Targeted QA coverage and review

Reviewed the supplied ACT Tests document against the Cosmos guide index and Markdown files at [the integration baseline](https://github.com/Double-FW/Cosmos-UX-Design/tree/c33e7a65083025977e2df198d5de67d54231a0c5). This is a documentation review. There are no results from a tested product, browser or assistive technology combination.

## Coverage

All **38 indexed design patterns** have an existing testing section. **20** link to at least one supplied suite, including suites that cover only a specific variant or a shared behaviour. **18** have no corresponding suite in the attachment. The table flags both situations. **37** link to at least one W3C ACT rule. **Tooltips** has existing component ACT-style test cases and no linked W3C ACT rule. A linked W3C rule checks its defined assertion, such as whether a button has a name. It does not establish coverage of the surrounding pattern or service journey.

## Contradictions and applicability

The imported suites retain their source wording. Apply these review decisions before adapting a script to the host QA framework. Resolve the intended variant before scoring an assertion where the suite and Cosmos expect different behaviour.

| Area | Finding | Recommended interpretation or change |
| --- | --- | --- |
| Accordions and disclosure | The accordion suite expects authored `aria-expanded` on every control. Native `summary` exposes its state through the browser. Exclusive groups can close another item, and a variant that requires one open panel may constrain closing. The disclosure script can also be misapplied to a preview that deliberately focuses its continuation point. | Test the exposed role and state in both native and custom variants. Check authored `aria-expanded` only for custom controls. Give independent, exclusive and keep-one-open configurations separate fixtures. Use the continuation-focus check for the expanded-preview variant. |
| Cards and promos | Cards expects the headline before all text alternatives and prescribes a list and heading hierarchy for every collection. Promos and the Cosmos promo guide allow an informative image before the headline. The promo suite requires a headline link even for patterns now used for previews or separate actions. | Scope headline order to the link-led fixture. For an informative image, assess whether the image-first reading order makes sense. Apply list semantics to a collection where a list conveys its structure. Check heading levels in the surrounding document. Use the guide’s own playback and secondary-action checks. |
| Contrast and target size | Several suites use a single 4.5:1 rule for normal text, icons, status cues or focus. Some apply 24 by 24 CSS pixels as an unconditional target-size minimum. | Use [Colour, Contrast and Meaning](../Colour%2C%20Contrast%20and%20Meaning.md#contrast) and [Call to Action](../Call%20to%20Action.md#give-pointer-users-room-to-activate-the-action) to scope text contrast, large text, essential non-text contrast and applicable target-size exceptions. Treat focus visibility as its own check. Record a stricter target as product policy when confirmed. |
| Focus and keyboard | The Focus suite says only interactive elements should be keyboard focusable. Data Tables may need a keyboard-reachable scrolling wrapper. Tabs, modal dialogs and client-side routing can programmatically focus static content. Radio groups use the native group keyboard interaction. | Distinguish a sequential Tab stop from programmatic focus and from focus inside a composite. Assess what the stop does for the user. For radios, verify entry, arrow-key selection and exit. For checkboxes, verify individual Tab stops and Space. |
| Form validation | Expectation 7 refers to a headline link and metadata strip. It repeats Promo Expectation 7. The suite expects an explicit false state after correction, and its blanket visible-label expectation omits the compact search exception. | Exclude Expectation 7 from form scoring. Use the promo test once. Apply the compact [Search field labels](../Search.md#search-field-labels) case only to that variant. Accept `aria-invalid="false"` or removal after correction. Distinguish a fresh form from a server-rendered form returning validation errors. |
| Grids and data tables | The grid and table suites overlap on preserving header alignment. The grid title can suggest an interactive ARIA grid. The data-table fallback role checks do not cover the keyboard contract for an interactive grid. | Use Layout for CSS grid order and reflow and Data Tables for tabular relationships and overflow. Retain the native-table and ARIA-table cases as separate fixtures. An interactive grid requires its own criteria for navigation, selection and editing where present. |
| Headings and routing | The title, first-heading and skip-link assertions overlap with Page Structure. The routing script requires heading focus for every route change. Cosmos can restore the prior results position on Back or Forward. | Reuse shared title, heading and skip-link checks. Split routing into direct load, in-app navigation and history restoration. Test the return position or heading based on the history contract. Evaluate a heading fixture in its surrounding page before scoring hierarchy. |
| Iconography and alternative text | The iconography suite requires `focusable="false"` based on legacy browser behaviour. The alternative text suite assumes a particular announcement or visible fallback, which depends on the chosen rendering and assistive technology. | Verify decorative SVGs add neither a Tab stop nor an extra accessible name. Apply legacy markup where the support matrix calls for it. For images, check equivalent meaning and task operability with images unavailable. Test meaningful and decorative images, functional images in controls and complex-image alternatives separately. |
| Tabs | The imported suite puts every tab in the Tab sequence and moves focus to the panel on activation. Cosmos also documents standard tabs, where arrow keys move within the tab list and activation keeps focus on the tab. Source anchors and Back/Forward behaviour depend on URL integration. | Use the supplied focus expectation only with the documented focus-moving variant. For standard tabs, run the guide’s roving-focus checks for the implemented activation model. Run URL and browser history cases only when the variant exposes that behaviour. |
| Call to action and links | The suites share control naming, keyboard and voice activation checks. A CTA can be a link or a button. “Click” commands and exact speech differ between tools. | Run the common naming assertions once per fixture. Test Enter for an ordinary link and Enter and Space for a native button. Use commands supported by the host voice control and check the action. Use the new-tab case where a link actually opens a new tab. |
| Carousels and sliders | Carousel checks cover paged slides. They do not cover a freely scrolling collection or a value slider. The suite expects slide position announcements without distinguishing manual selection from automatic changes. | Test the implemented carousel variant. For optional rotation, check opt-in, stopping on focus or hover, explicit restart and reduced motion. Announce meaningful user-initiated changes without announcing every automatic transition. Use separate tests for native scrolling and range inputs. Where more than one carousel is present, test whether people can distinguish the groups and controls, traverse the page and read nearby content without competing updates. |
| Dark mode and toggles | The source uses “Auto” where Cosmos uses “System”. The generic toggle suite alternates between switch and toggle-button terminology. Media action buttons may change their name and have no pressed state. | Verify the actual labels and a system-theme change, reload persistence and forced colours. Expect a switch’s checked state, a toggle button’s pressed state, or the current action name for a changing-label command. Do not use switch speech as the expected result for all three. |
| Modal dialogs | Case 6 opens a second modal inside the first. The guide prefers one modal at a time. The suite also places “On Focus” under 2.4.3. | Scope the case to an existing stacked workflow. Test that only the top modal can be operated and that focus returns to the correct trigger after each close. Keep the 2.4.3 focus-order check distinct from 3.2.1 On Focus. |
| Navigation menus and pagination | The menu check always returns focus to the opener on Escape. Mega Menu distinguishes focus inside the panel from focus already on another control. Numbered pagination, breadcrumbs and Load More have different destinations and state changes. The pagination suite implies that an ellipsis needs a particular announcement. | Use Escape expectations from the owning navigation guide. Run paged-navigation cases only for actual pagination. Test current-page state, meaningful link names and destination changes. For an ellipsis, decide whether omitted pages convey useful information or whether the glyph is decorative. |
| Progress and notifications | The progress suite expects a keyboard focus stop for the indicator. Cosmos uses passive status messages and independent controls to operate a task. A progress bar’s value and a spoken status update are separate outcomes. | Test discoverability and exposed values for passive progress without introducing a Tab stop. Verify determinate and indeterminate states, announcements at meaningful intervals, completion, failure and retry. Test any cancel or retry control in the ordinary focus order. |
| Skip links | The skip link suite overlaps with routing, keyboard navigation, landmarks and Page Structure. Checking a visible scroll alone misses focus and the next Tab destination. | Reuse one procedure across implementations. Verify initial discoverability, arrival at the intended target, and the next Tab or screen reader reading position. Document the separate mechanism if a product bypasses repeated content another way. |

## Duplication and source ambiguities

- Run shared keyboard, naming, focus visibility, forced colours, resize and script-failure checks once for the same assertion in the same variant, state and environment. Link the evidence from the other applicable test records. Repeat when a different variant or task changes the expected result. In particular, reuse the common checks in Accordion and Disclosure, Cards and Promotional Cards, Routing and Skip Link, and Navigation Menu across site, global and mega-menu fixtures.
- The attachment mixes short expectations, expanded procedures, repeated outcomes and incomplete conformance mappings. Some numbering has gaps. Preserve those identifiers. Assign a stable host ID when adapting each procedure, document the source heading and score the observable outcome. “Required for conformance to” without a named standard and “needs further testing” do not resolve which criterion to assess.
- Naming and role checks can often use computed accessibility-tree data. Meaning, usable focus order, announcement timing, voice use and completion or recovery need context or direct observation. Treat sample speech as illustrative. Report the supported environment and commands used.
- Measure text resizing separately from reflow. An existing case at 200% text size does not verify 320 CSS pixel reflow. Exercise forced colours independently of colour-vision simulation and compare script-blocked and CSS-disabled states where the component has a fallback.
- Existing guides often list the same W3C rule in testing and Sources. The local rule copy is shared by ID. For `6cfa84`, retain the published and proposed source links and check the specific version’s assumptions before scoring a dynamic state. A reference to a related rule inside a copied W3C rule is part of that upstream material.
- The existing Tooltips Cases 1 and 2 overlap with the guide’s own screen reader and pointer checkpoints. Use the guide’s interpretation of a hidden tooltip: its text may be available as the trigger’s description without creating a separate item in reading or focus order.

## Highest-priority coverage gaps

1. **Service journeys.** Extend the existing scripts for authentication and recovery, checkout and payment interruption, saving/resuming, cancellation and support handoff with cross-step scenarios. Confirm whether people can complete the task without losing entries, preferences, context or access to a non-default route. W3C naming rules alone do not exercise these outcomes.
2. **Complex controls.** Add fixture-level coverage for date typing and calendar navigation, keyboard and single-pointer alternatives to dragging, slider bounds and steps, caption and audio-description controls, rating input and persistence. Include any host-specific composite keyboard contract.
3. **Feedback and progress.** Create targeted scenarios for delayed responses, retries, repeat announcements, notification review, and chatbot escalation. Check where focus remains, what is announced, and what can be read later. Exercise disabled enhancements where relevant.
4. **Pattern-specific scope.** Define standalone applicability for numbered pagination, passive progress, and switch versus toggle button before treating their shared tests as complete pattern suites. Add a tooltip-specific W3C ACT reference only if a rule’s actual scope matches the intended assertion.
5. **Reproducible evidence.** Add representative fixtures, supported browser and assistive technology combinations, test data, pass/fail examples and expected state transitions where the source is vague. Run the resulting procedures in the host before recording release evidence.
